## Facts

- **Server links** (batch 2, capture-validation §7): plaintext, README framing, no seed or cipher. Either end sends
  `0x0804` after 30 s without receiving on that link; the other end answers `0x0805`. Per listener: AccountDB 2 links
  (Login, WM), AccountLogDB 2 (Login, WM), Login 1 (WM), WM-zone port 16, CharDB 17 (WM + 16), GameLog 18.
  4 of the 16 WM-zone links get the WM broadcasts (one per zone process). 4 links per zone process to each of WM,
  CharDB and GameLog: `SocketBundle<…>` `sb_SocketStr[4]` (pdb2016), `sb_GetSocket` @ FUN_004199b0 picks the next one
  for **every send** (captured as a strict rotation); the WM replies on the request's link. A zone's save burst is
  therefore spread over 4 links and applied by the WM interleaved by link (capture-validation §7.5.1).
- Each login sends two WM→zone `0x0C16` kicks per zone: one on Login's `0x0C16`, one on the client's WM `0x0C0F`.
- Batch-2 pcapngs mix a LAN and a loopback interface; frames are not in timestamp order in the file. Sort by
  timestamp (one shared clock) before reading an order.
- Login and WM seeds: per-server counter `(prev + 1) % 499`, initial `rand()` (Login ctor @ FUN_00409680,
  `ActiveSession` @ FUN_00409700). Zone: global counter `seed` in `ShinePlayer::so_EncSeedSet` @ FUN_0054f660 (`+1`, reset to 0 at 499), called on
  accept: first connection after start = 1, then consecutive *(captured: 9210 1, 3, 4, 5; 9212 1, 2; 9214 1)*, as Z18 §1.3
  (not Z01 §5.1's `newseed`, the dead 0x0806 path).
- `0x0C0C`/`0x0C0D` validate key: XOR of the 32 words = per-world counter `(+1) & 0x7FF`
  (`GetClientValidation` @ FUN_0040a200); the 31 random words are 15-bit.
- The captures contain no SYN/ACK frames (saved as displayed packets); the decoder's resync at offset 0 no longer
  discards a captured seed (fixed in `pcap_decode.py` by P02). Several game packets often share one frame (up to 67).
- 0x3C01 `npcPosition` (link-gate menu) = the player's server-side position `p+0x66`: `NPCRole_Portal::nrb_Role`
  @ FUN_004c2ef0 passes NULL to `sp_ServerMenuOpen` @ FUN_0054eaa0, which then uses the player's location.
- 0x2402 for NPCs: SP = `ShineMob::so_GetSP` @ FUN_00556940 / `so_MaxSP` @ FUN_00556920 = MobInfoServer `MaxSP`
  (100 for Gate_Town and MapLinkGate).
- WM client session handle = slot + k · 2500 (`nMaxAccept` of the WM client listener in ServerInfo.txt), +2500 per
  reuse of a slot (W05 §4.2 confirmed).
- The 2016 client sends unsolicited `0x0805` to the WM from `World::LoadMap` (FUN_006768c0) via FUN_006d2ef0
  (`NetMgr::SendHeartBeat2WorldMgrServer`, pdb2017 name), so long map loads do not trip the WM heartbeat.
- AVATAR `sKQMapName` / `nKQCoord` / `dKQDate` hold the last saved map, position and time even with `nKQHandle` = −1;
  a new character has the creation time in `dKQDate` *(meaning inferred)*.
- WM order after zone 0x180C (map login done, `fc_NC_MAP_LINKEND_CMD` call order): (party / raid refresh if any),
  0x1097, 0x1012, 0x9414, (friends, chat-restrict, spam-filter if any), 0x5826, 0x10D9, 0x0849 and the zone 0x1120 +
  CharDB attendance request (first map login only), 0x182A, 0x5425 (only if friend points changed), GameLog 0x040F; the client's 0x581B answer races with this burst.
- Zone map login (all 7 captured): the blob copies (0x1038 … 0x441E, W01 §6.3 order) arrive **before** 0x1802; the
  0x1803 burst is one server tick; the parameter refresh (0x1035 full, 0x240E, 0x240F, 0x245F) follows one tick later;
  StaImmortal 291 (5 s login protection) is reset by 0x2428 after 4.93–5.02 s.
- The 2016 client sends `NC_ACT_CHAT_REQ "&adminlevel"` and three `0x200B` in the same tick as every 0x1803, and
  `0x302C {0}` + `0x3020 {0}` after the first 0x1803 of a session only.
- Zone player handles: 8000 + pool index, allocated in order per zone process (8000, 8002, 8003, 8004 …).
- `0x1802.logincoord` is the position after `so_MapMarking`; it can differ from `0x1038.currentcoord` (x + 25 seen).
- Zone heartbeat to the client: 0x0804 after 30.0 s of client silence (`ClientSession::CheckHeartBeat` @ FUN_0045b110).
- In-world (single player): the client reports moves with `0x2019` / `0x2017` every 0.1–0.4 s (`to` ≈ 100 units
  ahead) and `0x2012` on stop, before an NPC click and before `0x1071`; the server answers only failures (`0x201B`).
- Mob moves: `speed` = MobInfo.WalkSpeed / RunSpeed (154 of 154); `from` = previous `to`; `moveattr` stale with bit 0
  cleared (Z02-B2). Objects enter sight with `0x1C08` (+ the remembered move, `from == to` if it has arrived) and leave
  with `0x1C0E`, both at the 1600-unit `MapInfo.Sight` of the three captured maps.
- NPC click order: `0x2401` → `0x2402` → `0x200A` → `0x243D` (next tick, own handle) → `0x201C` (NPCMenu 1) or `0x3C01`

- Per-minute player check: two 10-entry `0x1035` (flags 0x12–0x1B) one tick apart (the minute block's own
  `smo_NotifyParameterChange(1)`, then the `so_Routine` dirty-flag pass on `p+0xe94` @ FUN_0056a080), same wall-clock second on every
  zone process. Expiry of 1-day items inside it: `0x3002 {box 8 slot, item 0xFFFF}` per item, `0x10BD {0x1E00, 0}`
  when the pick-up mini-mon goes, then a full `0x1035`, `0x240E`, `0x240F` (GameDB 0x3459 / 0x345A round trip, one tick).
- Abstate 728 = `StaE_UserNewbie01` (10 min): granted on the first map login of a session via WM
  `CWMClientSession::Send_NC_CHAR_SUPPORT_REWARD_CMD` @ FUN_00433ab0 (W04's `Session_SendSupportReward`) → zone `0x1120 {nCharNo, eUserType 2}` @ FUN_005a5c70 (W04 §17.5, Z07 §1.2),
  one server tick after the 0x1803 burst; later map logins carry it in the `asl_SendAfterLogin` batch.
- Decoder type forms (since part 5): `T[]`, `bytes` (rest of payload), nested `Outer::Inner` by suffix, inline `{u8,u8}`,
  `struct[n]` + `name[i].member` overlays, `datasize`-prefixed elements; see `decode_ann` in `pcap_decode.py`.
- **WM ↔ CharDB link** (batch 2, capture-validation §7.4): every CharDB→WM character block starts with the WM
  `clienthandle` (u16) except 0x541C, 0x9427 / 0x9429 / 0x9444, 0x702C–0x702F, 0x1114, 0x111E (no handle) and 0x1121
  (its own `nWorldHandle`); P02.json `packets.wm` has the shifted layouts. The 36 blocks + 0x1005 of one load arrive in 17 ms; the WM
  needs ≈ 580 ms to handle them (one packet per session per main-loop pass, ≈ 15.6 ms per pass, W05 §1.4).
- **Map-login hand-over** (batch 2, capture-validation §7.5.2): 0x1801 → 0x104B → 0x104C → 0x101C → 31–33 WM packets (0x101D included) in
  one ms on one link → 0x1802 391–455 ms later: the zone handles one packet per link per pass (≈ 13 ms), so the
